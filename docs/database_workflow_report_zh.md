# 會員資料庫工作流程分析報告

## 1. 專題背景

本專題是一個以 SQLite 建立的會員管理資料庫系統，屬於 **Introduction to Database Systems / 資料庫系統概論** 課程專題。

這個系統主要負責管理：
- 會員資料
- 繳費資料
- 運動活動資料
- 活動報名資料
- 管理員資料

這個專題最重要的概念是：資料庫不只是存資料，還會自動檢查規則，避免錯誤資料進入系統。

## 2. 資料庫核心結構

### 資料表

| 資料表 | 功能 |
|---|---|
| `Member` | 儲存會員基本資料與會員狀態 |
| `Payment` | 儲存繳費紀錄 |
| `SportsEvent` | 儲存活動資料 |
| `EventRegistration` | 連結會員與活動的報名資料 |
| `Admin` | 儲存管理員資料與角色 |

### 關聯關係

- 一位會員可以有多筆繳費紀錄。
- 一位會員可以報名多個活動。
- 一個活動可以有多位會員報名。
- 每一筆繳費只屬於一位會員。
- 每一筆報名都會連結一位會員與一個活動。

## 3. 系統如何運作

整體流程如下：

1. 建立資料庫結構。
2. 新增或更新資料。
3. 由約束條件檢查基本合法性。
4. 由觸發器處理業務規則。
5. 透過檢視表產生報表。

### 3.1 建立資料表

`init_database.sql` 會先建立所有 tables。

也就是說，資料庫一開始就知道資料格式是什麼，之後才可以存資料。

### 3.2 資料輸入

使用者或腳本可以新增：
- 新會員
- 繳費紀錄
- 活動資料
- 活動報名資料

在這個階段，資料庫會立刻檢查資料是否正確。

### 3.3 約束條件檢查

基本驗證由 SQL constraint 完成：

| 約束類型 | 功能 |
|---|---|
| `NOT NULL` | 防止必要欄位是空值 |
| `CHECK` | 驗證格式與規則，例如 email 或金額 |
| `UNIQUE` | 防止重複資料 |
| `FOREIGN KEY` | 確保關聯資料存在 |

本專題的例子：
- Email 必須像真正的 email。
- 繳費金額必須大於 0。
- SID 必須唯一。
- 同一位會員不能重複報名同一個活動。

### 3.4 觸發器處理

當某個規則需要「自動動作」或「跨表檢查」時，就使用 trigger。

| 觸發器 | 功能 |
|---|---|
| `trg_activate_member_on_payment` | 繳費後自動把會員狀態改成 `Active` |
| `trg_check_active_before_registration` | 阻止非 Active 會員報名 |
| `trg_check_event_date_before_registration` | 阻止報名已過期的活動 |
| `trg_check_payment_date` | 阻止未來日期的繳費 |
| `trg_unique_event_name` | 防止同名同日期活動重複建立 |

觸發器很重要，因為只有 constraint 不足以處理所有業務邏輯。

### 3.5 檢視表報表

檢視表是預先寫好的查詢，用來做報表：

| 檢視表 | 功能 |
|---|---|
| `vw_MemberList` | 顯示所有會員資料 |
| `vw_MembershipStatus` | 顯示會員狀態與繳費統計 |
| `vw_PaymentReport` | 顯示繳費紀錄與會員資料 |
| `vw_EventList` | 顯示活動與報名人數 |
| `vw_EventRegistrationReport` | 顯示完整報名資訊 |

## 4. 為什麼使用 Trigger，而不是只用 Constraint

這是這個專題最重要的重點。

### Constraint 適合簡單規則

例如：
- 不可空值
- email 格式
- 金額必須為正數
- 不可重複

### Trigger 適合動態規則

例如：
- 自動更新另一張表
- 檢查其他資料表的內容
- 在動作發生前直接阻止

### 例子

當新增一筆繳費時：
1. 先檢查付款日期
2. 再檢查繳費金額
3. 最後自動把會員狀態更新成 `Active`

因此，這個系統非常適合使用 triggers。

## 5. 工作流程例子

### 例子 A：會員繳費

```text
新增繳費資料
   -> 檢查日期是否為未來
   -> 儲存繳費資料
   -> 觸發器自動把會員狀態改成 Active
```

### 例子 B：會員報名活動

```text
新增報名資料
   -> 檢查會員是否為 Active
   -> 檢查活動日期是否已過
   -> 通過後儲存報名資料
```

### 例子 C：查詢報表

```text
讀取檢視表
   -> 資料庫自動 join 多個資料表
   -> 顯示成報表
```

## 6. 專題設計優點

- 資料規則直接在資料庫層被保護。
- 不依賴某一種程式語言。
- 報表可以透過 views 很容易產生。
- 很適合資料庫課程展示，因為可以清楚表現 SQL 功能。

## 7. 限制與未來改進

- 管理員部分目前比較像資料存放，還沒有完整登入系統。
- 狀態欄位目前是文字型態，未來可以改成更嚴謹的參照表。
- 可以增加更多統計報表。
- 可以加入 audit log 紀錄誰改了什麼資料。

## 8. 結論

這個專題利用 SQLite 的 tables、constraints、triggers 和 views 建立完整的會員管理流程。

最重要的概念是：資料庫不只是被動儲存資料，而是會主動保護資料品質並自動執行商業規則。

新手最簡單的記法是：
- tables 用來存資料
- constraints 用來擋錯誤資料
- triggers 用來自動處理規則
- views 用來顯示報表
